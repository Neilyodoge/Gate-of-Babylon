# TA-261 · glTF 顶点色带上 Alpha 后，R 蒙版为何变粗

**制作决定。** 顶点色 R 做很窄的材质混合时，先核对资产里的原值、glTF `COLOR_0` 和导入 Mesh。这个 Blender 导出版本的普通路径中，同一份 Float Color 保留 Alpha 会把整个 `COLOR_0` 从 RGB Float32 改为 RGBA UNorm16；Unity Mesh 后来显示 Float32，不能恢复文件里已经合并的两个值。

## 公开证据

- **Blender 源属性。** [Blender 4.5.0 的 Byte Color 接口](https://github.com/blender/blender/blob/v4.5.0/source/blender/makesrna/intern/rna_attribute.cc#L424-L454)把字节存储的 RGB 从 sRGB 读成场景线性值；通过线性接口写入则先转成 sRGB 再存字节。读取得到浮点表示，数据仍源于每通道 8 位；把此图层转成 Float Color 后要从原始蒙版重填，才能找回先前损失的阶数。
- **Blender glTF 导出。** KhronosGroup 4.5 维护分支固定提交 `19602b6` 中，[常规颜色输出类型](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L1267-L1284)按是否带 Alpha 选择三分量或四分量，再由[类型映射](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/com/conversion.py#L98-L106)写为 Float 或 UnsignedShort。四分量走[夹到 0–1、乘 65535、就近取整、标上 normalized](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_attributes.py#L184-L219)，R 也一起量化。另有[填 255 的占位颜色](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L1194-L1205)使用 UNorm8。glTF 2.0 [规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#meshes)本身允许 `COLOR_n` 使用 VEC3 或 VEC4，以及 float32、UNorm8 或 UNorm16；有 Alpha 也允许 Float32，这是导出器的取舍。
- **Unity glTFast 6.10.0。** 该版本包镜像的普通颜色路径把 [VEC3 Float 补 A=1](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/Jobs.cs#L908-L925)，将 [RGBA UNorm16 除以 65535](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/Jobs.cs#L977-L1003)，最终统一[写入 Unity Mesh 的 Float32×4 色流](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/VertexBufferColors.cs#L66-L79)。RGBA UNorm16 的文件原始颜色数据是 8 字节／顶点，导入代码声明的颜色流是 16 字节／顶点；普通路径下文件变小不代表运行时色流也变小。具体 Mesh 总大小、GPU 带宽和压缩扩展路径未测。

## 阈值算例和排查

给两个三角形各自所有角填一个相同的线性 R，分别为 `0.500019` 和 `0.500023`；让材质阈值为 `0.500021`，先用 Float32 比较。按 CPU 复算，RGB Float32 仍一低一高；RGBA UNorm16 两者都写为 `32769`，解码后约 `0.50002289`，都通过阈值。同一个文件码在 Mesh 中也只有一个浮点值；应先追到两者在哪一步合并。

**最小对照（未执行）。** 固定三角形、Float Color 源数据和 R 阈值，只切是否保留 Alpha，先关闭额外压缩与导入后处理。分别看 `attributes.COLOR_0` 指向的 accessor（`type`、`componentType`、`normalized` 和两组实际 R）、Unity Mesh 的颜色格式与读值，再看取消光照的阈值输出。若源值在 Blender 已相同，回查存储类型和上游烘焙；进文件才相同就修导出或调整混合范围；文件仍有差而 Mesh 没差，再查导入器。如果必须保留真正的 Alpha，可试让导出保留 Float32 RGBA 或把蒙版迁到接收端确认支持的独立流；两种都要另验兼容性和运行时顶点开销。

**验证状态。** 已核对公开源码、glTF 2.0 规范和 CPU 算例；未在 Blender 实际导出、未在 Unity 导入或抓帧、未测试目标设备。

## 保留 Alpha 时把精细蒙版放到 UV 的 U

**制作决定。** 对这组固定版本的普通导出和导入路径，把 Alpha 留在 `COLOR_0`，把精细标量放入空闲 UV 的 U。先核对项目的贴图和烘焙光照占用，再定槽位；用实际 Mesh 的属性表确认蒙版到了哪里。

**文件有字段，Mesh 未必有。** Blender 打开[自定义属性导出](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L183-L226)可写 `_MASK`，打开[全部顶点色](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L802-L829)可写后续 `COLOR_n`。glTFast 6.10.0 的[顶点属性字段](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/Schema/MeshPrimitive.cs#L192-L232)只有一个颜色字段；普通 [颜色 Job](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/VertexBufferGenerator.cs#L337-L359)只接 `COLOR_0`，[Mesh 顶点布局](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/VertexBufferGenerator.cs#L391-L435)也没有接收任意属性的分支。仍以 `COLOR_1` 或 `_MASK` 命名的蒙版即使在 glTF 内有正确实值，也不会由这条路径自动成为 Unity Mesh 的顶点属性。

**UV 是已接入的路径。** Blender 按图层顺序把[普通 UV 写成 `TEXCOORD_n`](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L258-L265)，[文件用 Float32×2](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L1658-L1667)。glTFast 这条 UV 路径[从 0 连续数编号](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/Schema/MeshPrimitive.cs#L261-L274)，[前八组受支持](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/VertexBufferGenerator.cs#L98-L120)，按顺序[写入 `VertexAttribute.TexCoord0 + n`，声明 Float32×2](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/VertexBufferTexCoords.cs#L113-L131)。检查时按编号用 `Mesh.GetUVs(n, …)` 读值；新增一组 UV 为每个输出顶点增加 8 字节的声明数据。如共享顶点各个面角的蒙版不同，导出器[将属性放进面角去重键](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L326-L337)并[按完整记录去重](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L831-L842)，输出顶点数也可能增加，另查 `POSITION` accessor 的 `count`。

**为什么优先 U。** [Blender 导出](https://github.com/KhronosGroup/glTF-Blender-IO/blob/19602b6a033bccd99763327c1e47a22d93db1d3b/addons/io_scene_gltf2/blender/exp/primitive_extract.py#L1423-L1435)与 [glTFast 导入](https://github.com/needle-mirror/com.unity.cloud.gltfast/blob/9347dca0f7a2ed5a0f465ec184d29ce7778ad62e/Runtime/Scripts/Jobs.cs#L1189-L1199)都对 V 做一次 `1-v`；U 在这两个步骤原值通过。用 Float32 逐步复算，输入 `0.10000000` 和 `0.10000002` 分别低于和高于阈值 `0.10000001`。放进 V 时，两者在文件中都变成约 `0.89999998`，导入后都变成约 `0.100000024`。这只说明极窄阈值会受坐标翻转舍入影响；常规 UV 不一定可见此差异。

**最小对照（未执行）。** 固定三角形、Alpha、两个蒙版值与 Float32 阈值，仅改同一蒙版的承载位置：`COLOR_1`、`_MASK`、空闲 `TEXCOORD_n` 的 U 和 V。先验文件字段和原值，再验 Unity Mesh 的顶点声明、数值和阈值结果；若复用现有 UV，另对照材质采样及光照烘焙。关闭压缩和额外导入后处理，分别记录 `POSITION` 数量及 UV 流数据。已核对固定源码和 CPU 算例；未导出、导入、抓帧或在目标设备验证。
