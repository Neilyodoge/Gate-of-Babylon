# 自研 GPU 蒙皮：先把动态包围盒和骨权重成本分开测

**一句话结论**：同一 Compute Pass 同时变形顶点和计算动态包围盒时，先查是否所有顶点都在争写同一个盒子。若是，限骨权重可能牺牲关节变形，却绕不开主开销。

## 公开测量：骨权重没变，蒙皮 Pass 从 7.0 ms 降到 1.7 ms

[Traverse Research，2026-10-02，Breda 渲染器开发复盘，§01/02/07](https://traverse.nl/blog/gpu-skinning-without-global-atomics/#skinning-is-cheap-the-bounds-were-not)。Breda 把已变形顶点写到 GPU 缓冲供光追加速结构使用，同时计算每个蒙皮网格的动态 AABB。旧实现让每个顶点对同一个网格的六个全局极值做原子 min/max。Evolve 在一台零售 Android 手机上的作者测试，#10011 只改了包围盒归约：先在 wave 内求极值，只由首个 lane 写全局，`apply_vertex_bones` 的记录是 **7000 → 1700 μs**。骨权重和蒙皮计算在这组对照中未改。文章没有列手机型号、API、样本分布或总帧时，因此此数仅是该负载的 Pass 时长。

作者后续把动态包围盒做成两级归约：每组把局部盒写入自己的槽，另一个 Pass 按网格合并，免去对于同一盒的全局原子争用。需要临时缓冲和额外调度；64 线程一组时，每个网格尾组最多有 63 个无效 lane，数千个小网格未必合算，原文尚未测这个交叉点。另一候选是合并各骨骼的保守包围盒，降低计算量但可能增加剔除误报和后续工作。

同一后续改动还压缩骨矩阵、骨骼索引与权重，并改变法线计算。文中 **564 → 220 B/顶点** 是该实现按缓冲布局算出的读取字节，**不是实测 DRAM 流量**；也不能把合并后的改动归功于单一措施，或把 #10011 的时间挪给后来版本。权重打包仍保留四个影响，要另外验量化误差；它和把四个影响删到两个是两种改动。

## 采用前最小对照

1. 在可修改的 GPU 蒙皮测试场景中，固定网格、动画、骨权重、相机与可见集合。临时改为固定的保守包围盒，单独比较蒙皮 Pass，估算动态归约所占比例。性能对照阶段保持剔除结果一致；回到完整链路再记录深度、阴影、可见网格数量与总帧时。
2. 若归约占大头，再用少量大网格与大量小网格两类负载，比较逐组归约和保守盒的蒙皮、剔除与后续绘制总成本。若运行环境没有这个动态归约阶段，跳过这条诊断。
3. 若要回答“每顶点四权重减到两权重是否值得”，另开对照：固定顶点数、执行路径与包围盒方案，确认实际着色器读取/执行的影响数；先检查肩、肘、扭转姿势的轮廓与阴影，再测成本。公开案例没有回答这组 A/B。

**状态**：作者记录了一组 Android Pass 实测，后续布局字节为计算；本地未复现、目标设备未测，没有四权重与两权重的同素材形变对照。
