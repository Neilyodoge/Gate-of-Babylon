# ProjectR 变更影响检查

> 适用范围：`Babylon/Assets/1Game/` 与配套 `docs/`  
> 模块定义：[程序模块规划](程序模块规划.md)  
> 原则：改前确认爆炸半径，改后按实际文件复查，静态图与Unity运行验证并用。

## 1. 什么时候必须检查

以下情况必须先使用 `code-review-graph`：

- 修改公共类、接口、枚举、事件或ScriptableObject。
- 修改 `PlayerCombat`、`GameManager`、`SaveSystem`、`GameEvents`或Provider。
- 改动跨越两个以上程序模块。
- 变更存档、结算、技能释放、进房、清房、撤离等流程。
- 删除或重命名类、方法、序列化字段和Prefab组件。
- 通过切换闸门并准备删除Legacy路径。

单文件注释、纯文案和已知配置值调整可以只做精确搜索；若配置影响运行时分支，仍需检查调用方。

## 2. 工具入口

MCP可用时优先使用：

- `get_minimal_context_tool`
- `query_graph_tool`
- `detect_changes_tool`
- `get_review_context_tool`
- `get_impact_radius_tool`
- `get_affected_flows_tool`

当前根工作区不能稳定提供分支与diff时，不依赖 `detect-changes`；直接将计划或实际改动文件传给 `impact --files`。

## 3. 改前流程

### 3.1 声明任务

每批改动先记录：

- 主模块：只能有一个。
- 受影响模块：可以多个。
- 关联里程碑：M0～M5。
- 关联闸门：G1～G7或无。
- Legacy状态：不涉及／只读适配／准备删除。

### 3.2 检查图是否可用

1. 运行 `status`。
2. 图缺失、解析文件数异常或源码已变化时运行 `update --brief`。
3. 只接受 `Assets/1Game/Scripts/` 和 `docs/` 范围内的结论。
4. 排除 Edgar第三方源码、旧StsMap和共享工具库噪声。

### 3.3 查询结构

对入口类或关键方法查询：

- 谁调用它。
- 它调用谁。
- 谁实现或继承接口。
- 哪些测试覆盖它。
- 哪些执行流程经过它。

符号重名时必须使用图返回的 `qualified_name`，不能依据模糊名称直接下结论。

### 3.4 估算影响

对计划改动文件运行三跳 `impact`，将结果人工映射到模块ID。

高风险条件：

- 影响超过20个游戏文件。
- 跨越3个以上模块。
- 触及存档schema、结算或运行态提交。
- 触及公共事件、Provider或战斗接口。
- 影响Prefab／Inspector／动画事件但静态图不可见。

满足任一条件时，必须拆成更小批次并提供FeatureFlag或兼容适配器。

## 4. 实施约束

- 新路径默认放在独立模块目录。
- 中心类先委托新服务，不在原文件继续增加系统职责。
- Legacy只允许Bug修复和只读适配。
- 新旧路径并行时使用FeatureFlag，并明确默认值与回滚方法。
- 存档字段只增不删，迁移幂等。
- 器灵实例只通过撤离提交写入永久档。
- 蜂巢生态不写入 `EdgarMapProvider` 的空间生成职责。
- UI只读查询模型和事件，不直接写存档。

## 5. 改后流程

1. 列出实际改动文件，而不是复用计划列表。
2. 更新代码图。
3. 对实际文件重新运行 `impact`。
4. 对公共方法重新查询调用方。
5. 比较“预计影响模块”和“实际影响模块”。
6. 新出现的跨模块依赖必须修复或记录ADR。
7. 运行Unity编译、相关自动测试和Play Mode烟测。
8. 用Unity引用搜索检查Prefab、Inspector、UnityEvent、Resources和动画事件。
9. 更新程序架构、CHANGELOG、开发待办和相关系统规格。

## 6. 高风险契约检查

### GameEvents

- 事件发布者和订阅者是否完整。
- 场景切换后订阅是否恢复。
- `OnDestroy`是否取消订阅。
- 新回路事件是否携带来源与因果链。

### SaveData与SaveSystem

- schema是否升级。
- 旧档迁移是否幂等。
- 新列表是否在空档和旧档中初始化。
- Pause、AutoSave和强退是否会写入本局临时态。
- 死亡是否错误提交新器灵。

### PlayerCombat与载体

- 普攻、技能、身法、充能、蓄力和取消是否回归。
- `SkillCastStarted`及命中事件发布时间是否变化。
- 动画优先级和AnimationEvent是否仍匹配。
- Projectile payload和来源追踪是否完整。

### IMapProvider与Edgar

- GameManager、RoomFactory、事件房、商店和Debug调用是否兼容。
- 同一Seed是否复现。
- 回访是否重抽。
- 改门后模型、Collider和NavMesh是否一致。
- ProjectR模式是否绕开1004～1007专用逻辑。

### IDamageable与CombatStats

- 玩家、普通敌人、精英、Boss和可破坏物是否全部覆盖。
- 伤害来源、暴击、减伤、状态和死亡事件是否保持。

## 7. 跨模块验收流程

### 进局与首次攻击

模块：

- M-INPUT
- M-CARRIER
- M-COMBAT

必测：

- 输入到动作只有一条主路径。
- 伤害来源可追溯。
- 动画和技能资源正确。

### 器灵回路触发

模块：

- M-SPIRIT
- M-CIRCUIT
- M-COMBAT

必测：

- 深度、重复和单帧预算。
- 三种附着结构。
- 战后分析能解释主要结果。

### 换载体保留悟法

模块：

- M-CARRIER
- M-SPIRIT
- M-CIRCUIT

必测：

- 载体替换不清空器灵临时成长。
- 附着重排不会复制或丢失器灵。

### 进房、传播与清场

模块：

- M-DUNGEON
- M-ECOLOGY
- M-ENCOUNTER

必测：

- Seed复现。
- 生态快照固化。
- 回访不重抽。
- 门和NavMesh同步。

### 结契、死亡与撤离

模块：

- M-SPIRIT
- M-SAVE
- M-CORE
- M-UI

必测：

- 未撤离不永久获得。
- 撤离只提交一次。
- 死亡、读档、删档和强退不复制、不丢失。

## 9. 闸门通过规则

闸门只有同时满足以下条件才可勾选：

- 功能条件完成。
- 自动测试和Unity烟测完成。
- 改后代码图没有未解释的高风险依赖。
- 对应系统规格验收通过。
- 架构文档和CHANGELOG已同步。
- 明确列出可以关闭或删除的Legacy入口。

删除Legacy前再次对待删文件运行影响分析，并以精确搜索确认不存在代码、Prefab和Resources引用。
